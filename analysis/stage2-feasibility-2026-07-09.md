## 2. КЛЮЧЕВЫЕ БЛОКЕРЫ

### Блокер #1 (КРИТИЧЕСКИЙ): Stage 1 не подключён
**Факт:** `S1-WIRE/progress.md` — `⬜ Backlog, 0 phases completed`. Код Bee, TaskRouter, GrammarMutator, BeeWorker написан и протестирован в изоляции. Hive::tick() — монолит (строка 139-200), не использует ни одного Stage 1 класса.
**Влияние на Stage 2:** Без живой популяции пчёл невозможны: кросс-доменный перенос (3.2 — нужны пчёлы с разными грамматиками), эмерджентный язык (3.8 — нужен LawCompressor над пулом законов), модель последствий (3.7 — нужны действия пчёл). 
**Оценка:** 100% блокирует Stage 2. Без Stage 1 — Stage 2 недостижим.

### Блокер #2 (КРИТИЧЕСКИЙ): Семантический pipeline разорван
**Факт:** 895 text atoms открыто, **0 text-законов**. Причина: Forager извлекает single-column данные (`preg_match_is_a` даёт `subject, predicate, object`), но `Search::find` ожидает `X=[features], y=[target]`. E1.6 (data → law pipeline) не завершён: данные есть, X пустой, законов нет.
**Влияние на Stage 2:** Без семантических законов невозможны: 3.5 (семантическая стабильность — не на чем обучать stability law, нужно 47+ фактов + законы), 3.6-бис (кросс-валидация — нужны оба типа законов).
**Оценка:** Блокирует 3.5 и 3.6-бис. Без них Stage 2 пройти невозможно.

### Блокер #3 (ВЫСОКИЙ): Отсутствие LawCompressor
**Факт:** Ни одной строки кода. Протокол §3.8 требует: structural isomorphism detection → meta-law → grammar atom injection → cross-domain usage с compilation beats coalition.
**Влияние:** Блокирует 3.8 полностью. Частично блокирует 3.2 (нужен для обнаружения структурного переноса).
**Сложность:** Это NESTED-level задача — сравнение expression trees, нормализация констант, обнаружение изоморфизма с точностью до переименования переменных.

### Блокер #4 (ВЫСОКИЙ): Монодоменность открытий
**Факт:** 6 арифметических законов в одном домене `arithmetic`. 0 законов в других доменах. Демон циклится на DUPLICATE — плато достигнуто, новых данных нет.
**Влияние:** Для 3.2 нужно минимум 2 семантически различных домена с законами. Для 3.5 нужно разнообразие фактов.
**Причина:** Forager capped на 30 задачах, все из 6 метрик пользователя. Данные исчерпаны.

### Блокер #5 (СРЕДНИЙ): Search не масштабируется
**Факт:** D11: 551 ops → 8B комбинаций при depth=3 → 11 секунд. Grammar растёт с каждым открытием → search экспоненциально замедляется.
**Влияние:** При добавлении text atoms, compose-результатов, meta-law atoms — grammar взорвётся. Без pruning/cap search станет бесполезен.

### Блокер #6 (СРЕДНИЙ): Нет action logging
**Факт:** Требуется для 3.7. Текущий лог — текстовый agenda.log без структуры ACTION.
**Влияние:** Блокирует 3.7, но этот критерий — один из наименее зависимых.

### Блокер #7 (НИЗКИЙ): Нет /explain endpoint

## 5. КРИТИЧЕСКИЕ РИСКИ

### Риск #1 (ФУНДАМЕНТАЛЬНЫЙ): CV→0 на семантике принципиально не работает

**Суть:** CV→0 требует числового ratio: `e(x_i) / y_i`. Семантические данные (is_a, has, relates_to) не имеют числовой целевой переменной. Текущий подход: кодировать target как бинарный (0/1) — «факт верен» vs «факт неверен». Но:
- Бинарный target с 20 точками (10 positive, 10 negative) даёт CV→0 для ЛЮБОГО константного предиктора (всегда предсказывает 1 → ratio = 1/1 для positives, 1/0 для negatives → CV = ∞)
- Непрерывный confidence (0-1) требует градуированной истинности, которой нет в данных

**Файл:** `src/Core/Search.php:9-36` — cv() требует числовые векторы. Text atoms не производят числовых предикторов для семантических таргетов.

**Вердикт:** Это архитектурная проблема, не баг. CV→0 спроектирован для непрерывных данных. Применение к семантике требует либо (а) другого критерия, либо (б) непрерывной confidence через aggregation многих источников. Протокол предлагает второй путь (§3.5: stability law через CV→0 над историей фактов), но это мета-уровень: CV→0 над МЕТА-ДАННЫМИ фактов, а не над самими фактами.

**Импакт:** Если этот риск материализуется — 3.5 и 3.6-бис недостижимы. Stage 2 провален.

### Риск #2 (АРХИТЕКТУРНЫЙ): Grammar ceiling break (NESTED) не работает

**Суть:** Протокол §2.5-тер требует: система создаёт операцию, которой нет в стартовой грамматике. Текущий код:
- `GrammarMutator::mutate()` — случайные ADD/REMOVE/REPLACE из предопределённого пула `available` ops
- Compose — генерирует новые атомы как КОМБИНАЦИИ существующих: `×(min)` из `×` и `min`
- Ни один механизм не создаёт ПРИНЦИПИАЛЬНО НОВУЮ операцию

Для 3.8 (bee language) нужно: LawCompressor создаёт `stress_depletion` как новый атом из expression-tree-изоморфизма. Это создание НОВОГО ИМЕНИ для существующей структуры, но не новой СЕМАНТИКИ.

**Файлы:** `src/Hive/GrammarMutator.php`, `src/Core/AtomRegistry.php` (discoverCompose)

**Вердикт:** NESTED описан в ARCHITECTURE.md и протоколе, но в коде не реализован. Random mutation + compose ≠ создание новых операций. Без работающего NESTED: 3.8 (bee language) невозможен, 3.3 (GRAMMAR diagnosis) поверхностен.

### Риск #3 (ДАННЫЕ): Не хватает diversity открытий

**Суть:** Текущие данные — 6 пользовательских метрик из Journal. Даже с S1-WIRE и E1 fix, максимальное число доменов ограничено разнообразием данных пользователя. Для кросс-доменного переноса (3.2) нужно ≥2 семантически различных домена с законами. Если Journal содержит только персональные метрики — домены будут вариациями одного концептуального пространства.

**Файлы:** `src/Forager/Forager.php`, метрики в `~/Documents/the_lair/ExoCortex/Journal/`

**Импакт:** Без внешних данных (финансы, физика, биология, логистика) система не выйдет за пределы «персональная аналитика». Stage 2 требует мира за пределами пользовательского Journal.

### Риск #4 (МАСШТАБ): Поиск ломается при grammar > 1000 ops

**Суть:** D11: при 551 ops и depth=3 — 8B комбинаций. Добавление E1 text atoms (preg_match, extract_col, match_label + их compose-варианты) + meta-law atoms от LawCompressor → grammar > 1000 ops → > 50B комбинаций → search невозможен.

**Файлы:** `ProductSpecification/stories/d11-search-perf/progress.md`, `src/Core/Search.php:38-215`

**Вердикт:** Без grammar cap + pruning (D11) Stage 2 невозможен технически — система упадёт по таймауту на каждом тике. D11 — это не оптимизация, а survival requirement.

### Риск #5 (ПРОТОКОЛ): Нереалистичные требования к observation period

**Суть:** Stage 2 требует одновременного выполнения всех 10 критериев. Протокол не указывает период наблюдения явно для Stage 2 (в отличие от Stage 1: 7 суток). Однако:
- 3.1 требует предварительной регистрации + git timestamp
- 3.3 требует 10 нерешённых задач с верифицированными диагнозами
- 3.5 требует 47+ фактов для обучения stability law
- 3.8 требует N поколений эволюции

**Импакт:** Даже при работающей системе, накопление данных для 3.5 и 3.8 займёт недели непрерывной работы.

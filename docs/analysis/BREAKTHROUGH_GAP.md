## 2. АУДИТ ЦИФР: CLAIMS vs РЕАЛЬНОСТЬ

ARCHITECTURE.md заявляет: **61 закон, 192 grammar ops, 385 фактов, 93 модуля.**

### 2.1 61 «закон»

Что это на самом деле? Классификация: «какая из 27 имеющихся у меня функций соответствует этим данным?»

```
OR::or (CV=0)    — атом 'or' объясняет данные OR
AND::and (CV=0)  — атом 'and' объясняет данные AND
ADD::add (CV=0)  — атом 'add' объясняет данные ADD
```

Это НЕ открытия. Система не изобрела `or`, `and`, `add` — они были в стартовом наборе. Из 61: 9 — ручные базовые задачи (AND, OR, XOR, ADD, MUL, DIV, SQRT, SQUARE, MAX). Сколько по-настоящему новых законов на данных из metrics.jsonl или forager? Единицы.

### 2.2 192 grammar ops

Grammar::all() возвращает всё из БД. После нескольких запусков каждый открытый атом + каждый compose-вариант попадает в grammar_ops. Большинство из 192 — compose типа `sign(tanh)`, `abs(sub)`, `or(sq)`, которые получили CV=0 на крошечных синтетических данных из getTasks(). Это аккумуляция, не интеллект.

### 2.3 93 сгенерированных модуля

Одинаковый шаблон (~30 строк): атом применяется к фиксированному набору данных и проверяется CV. 93 файла = 93 инстанциации шаблона с разными параметрами. Это не «самокодирование». Это кэш-прогрев. Ни один модуль не вызывается демоном.

### 2.4 385 фактов в KG

Часть — ручной посев (seedBasicKnowledge: «объект is_a вещь», «человек is_a живой_объект»). Часть — forager с regex «X — это Y». Confidence 0.3 за первое обнаружение, +0.25 за повтор. Нужно 4 повтора для confidence=1.0. Сколько из 385 имеют confidence=1.0 и не из посева? Не измерено.

### 2.5 D/C ratio и Fidelity

Упоминаются в CUBE_IS_IT_AGI.md. Не вычисляются нигде в коде. D/C=1.81, fidelity=0.09 — вероятно, ручная оценка.

## 3. ПРОБЛЕМА ПЕРЕОБУЧЕНИЯ (OVERFITTING)

CV→0 на 3–7 точках — катастрофически слабый критерий. Что отсутствует:

1. **Train/test split.** Ни в discover, ни в compose нет разделения. Закон проверяется на тех же данных, на которых найден.
2. **Simplicity prior (Occam).** `(x0+x1)` и `(((x0×x1)+(x0²))−(x1×x0)+x1)` — оба могут дать CV=0. Система не различает.
3. **Minimum sample size.** 3 точки — не статистика. Для 2-входовой функции нужно 20+ независимых точек.
4. **Prediction test.** Система никогда не говорит «для x=7, y=3 предсказываю 10» и не проверяет.

**Следствие:** система находит не законы, а переобученный шум. CV→0 необходимо, но недостаточно.

## 4. ДЕМОН НЕ ДЕЛАЕТ ТОГО ЧТО ЗАЯВЛЕНО

agenda.php (~250 строк). Реальный цикл:

```
1. sys_getloadavg() — проверка CPU (НЕ ResourceGuard v2)
2. getTasks() — 9 базовых + метрики + compose-генерация + cloze
3. Если cloze → перебор grammar ops, минимальный error rate
4. Если не cloze → AtomRegistry::discover() (базовые атомы)
5. Если не найдено → AtomRegistry::discoverCompose() (пары)
6. Если не найдено → usleep(500000)
7. usleep(200000) — базовый тик
8. Повтор
```

**Чего НЕТ в демоне (вопреки ARCHITECTURE.md §6):**
- ❌ ResourceGuard v2 через /proc/self/stat (используется sys_getloadavg)
- ❌ Exponential backoff 2ⁿ (фиксированные sleep)
- ❌ Plateau detection >20 тиков → Forager
- ❌ Preload knownLaws из БД при старте
- ❌ H1 верификация старых законов
- ❌ LawCompressor
- ❌ D/C ratio измерение
- ❌ Отключение compose на плато

PLATEAU_PLAN.md описывает Фазу 1, тесты Phase1PlateauTest.php существуют — но в agenda.php изменений нет. Демон «v5» — это v2 + cloze.

## 6. ОТСУТСТВУЕТ ЗАМКНУТЫЙ ЦИКЛ С РЕАЛЬНОСТЬЮ

Все прорывные AI-системы имели замкнутый цикл:

| Система | Цикл |
|---------|------|
| AlphaGo | ход → результат партии → обновление policy → новый ход |
| AlphaFold | предсказание → сравнение с PDB → градиент → лучшее предсказание |
| GPT | предсказание токена → сравнение с реальным текстом → градиент |

**Bee Swarm:** наблюдение → CV→0 → запись в БД → ... ничего.

Нет действия. Нет проверки на новых данных, собранных специально для фальсификации. Нет цикла «предсказал → проверил → ошибся → исправился». Система — пассивный наблюдатель.

H1 (LawVerifier) частично решает это — но не подключён к демону.

## 7. СТРУКТУРНЫЕ ПРОБЛЕМЫ ПО КОМПОНЕНТАМ

### 7.1 Compose-взрыв не производит нового знания

`AND → ×(min), AND → ×(sq), AND → abs(×), ...` — 42 compose-варианта для одного атома. Комбинаторный взрыв, не открытие. Compose срабатывает на ВСЕ атомы, независимо от того, нужна композиция или нет.

### 7.2 KG и Search — два острова

KG содержит факты. Search про них не знает. Семантические атомы (is_a, has, can) определены в Grammar, но не участвуют в Search::find, потому что Search ожидает числовые данные. ConceptRegistry хеширует концепты через `crc32 % 1000` — коллизии гарантированы, и эти float'ы подаются в CV→0.

### 7.3 Cloze = adjacency test, не семантика

Проверка: «встречалось ли слово-кандидат в окрестности ±R слов от маскированной позиции?» Это не языковая модель. На 1000 предложений — статистически ничтожно.

### 7.4 Vikentiev curriculum отсоединён от демона

36/36 across 5 domains получены на КУРИРОВАННЫХ задачах с ручной настройкой грамматики. Демон не решает логические задачи, не открывает геометрические законы. Две разные системы.

### 7.5 Грамматика не эволюционирует, а комбинирует

Настоящая грамматическая эволюция требует: (а) доказать что существующая грамматика НЕ МОЖЕТ выразить закон, (б) изобрести НОВУЮ операцию невыразимую через существующие, (в) проверить что она открывает ранее недоступные законы. Сейчас — только (в), и то на данных которые уже решаются.

## 8. ЧТО ОТДЕЛЯЕТ ОТ ПРОРЫВА: СВОДКА

### Архитектурно

1. **Одна замкнутая петля вместо семи.** Forager→KG→Search→LawVerifier→Grammar→Search — этот цикл должен работать в рантайме.
2. **Классификация вместо открытия.** Система выбирает из предзаданного набора атомов, не изобретает новые. Compose — комбинация существующих, не создание новых примитивов.
3. **CV→0 на 5 точках без валидации.** Нет out-of-sample проверки, нет simplicity prior, нет минимального размера выборки.
4. **Нет контакта с реальностью.** Система не предсказывает, не ошибается, не корректируется.
5. **Архитектурная документация опережает код.** Это создаёт иллюзию что 7 слоёв работают, когда работают 2.

### Технически

6. Cloze — adjacency test, не семантика.
7. KG и Search не связаны.
8. ConceptRegistry — 1000-бакетный хеш, не embedding.
9. 93 модуля — кэш, не активные компоненты.
10. Нет self-measurement в рантайме (D/C, fidelity, discovery_rate).

## 9. БЛИЖАЙШИЙ ШАГ К ПРОРЫВУ

**Замкнуть петлю H1.** Подключить LawVerifier к демону. Каждые N тиков брать случайный старый закон, проверять на свежих данных. CV>0.1 → удалить. CV≤0.01 → confirmed. Вести счётчик confirmed/pruned.

Что это даст:
- Реальную диссипацию (не D/C на бумаге, а фактическое удаление ложных законов)
- Сжатие grammar (меньше шума → лучше поиск)
- Out-of-sample валидацию
- Измеримый прогресс (confirmed/pruned/deleted метрики)
- ~20 строк кода (LawVerifier уже написан и протестирован)

**Дальше — по порядку замыкания петель:**
1. H1 в демоне ← СЕЙЧАС
2. /predict + /verify эндпоинты (предсказание → проверка на реальности)
3. KG → Search мост (семантические атомы в поиске)
4. ResourceGuard v2 + exponential backoff + plateau detection (честный v5 демон)
5. ExoCortex-lite на чужих данных (воспроизводимость)
6. D/C ratio в рантайме (само-диагностика)

Один шаг за раз. Каждый шаг — замыкание петли, НЕ добавление модуля.

## 10. МЕТОДОЛОГИЧЕСКИЙ ВЫВОД

**Паттерн процесса:** «написал → протестировал в изоляции → не подключил → перешёл к следующему».

TDD гарантирует что код работает сам по себе. Но нет интеграционных тестов которые проверяют что компонент А вызывает компонент Б в рантайме. Поэтому демон v5 на деле — демон v2 + cloze.

**Что нужно:** после каждого нового компонента — интеграционный тест который запускает agenda.php на N тиков и проверяет что компонент вызвался. Или audit-скрипт который парсит agenda.php и сверяет список вызовов с ARCHITECTURE.md.
